# Маршрутизация SKU по складам — `warehouse_routing`

## Зачем

Раньше прогноз `forecast_stocks.py` строил строку по каждой паре `(sku × склад)`,
которая встречалась в свежем снапшоте `stock_marketplace`. В результате
в Telegram прилетала простыня типа:

```
🔴 ПВ4 / Ростов: остаток 0, скорость 0.4/день → ~0 дней. Рекомендую 8 шт.
🔴 ПВ4 / Яндекс.Маркет (Домодедово возвратный): остаток 0, скорость 0.4/день → ~0 дней. Рекомендую 8 шт.
🔴 ПВ4 / Склад 301: остаток 0, скорость 0.4/день → ~0 дней. Рекомендую 8 шт.
```

— хотя ПВ4 на этих складах вообще не торгуется.

Причин было две:
1. **Нет фильтра**: брались все пары из снапшота.
2. **Скорость глобальная**: считалась по всему marketplace и подставлялась
   к каждому складу одинаковая → ложные алерты.

## Что изменилось

1. Появился **новый лист `warehouse_routing`** — белый список пар sku × склад.
2. Скорость теперь считается **отдельно по каждому складу** из `ym_orders_raw`.
3. Прогноз идёт только по парам из routing. Всё остальное игнорируется.

## Структура листа `warehouse_routing`

Создайте в той же Google Sheets таблице новый лист `warehouse_routing`
со следующими колонками (первая строка — заголовок):

| sku  | warehouse                            | active | marketplace | comment             |
|------|--------------------------------------|--------|-------------|---------------------|
| ПВ1  | Ростов                               | Да     | YM          | основной склад      |
| ПВ1  | Ростов-на-Дону-2                     | Да     | YM          |                     |
| ПВ1  | Самара                               | Да     | YM          |                     |
| ПВ1  | Екатеринбург                         | Да     | YM          |                     |
| ПВ1  | МО Софьино (кроме КГТ) - 2           | Нет    | YM          | временно отключён   |
| ПВ2  | Ростов                               | Да     | YM          |                     |
| ПВ4  | Ростов                               | Нет    | YM          | не возим            |

**Правила:**

- `sku` — ID товара, как в `stock_marketplace` (колонка 2).
- `warehouse` — точное имя склада, как в `stock_marketplace` (колонка 5).
  Регистр и пробелы важны.
- `active` — `Да` / `Yes` / `1` / `true` / `+` → склад учитывается.
  Любое другое значение (или пусто после очистки) → склад игнорируется.
  Удобно использовать как мягкое выключение без удаления строки.
- `marketplace` — опционально. Если задан, фильтрует по нему;
  если колонки нет — считается что весь лист про YM. На будущее
  можно использовать тот же лист для Ozon/WB.
- `comment` — свободный текст для себя.

**Заголовок ищется автоматически** — допустимы 1–N пустых/intro-строк
выше шапки, как и в остальных листах.

## Поведение

| Сценарий                                              | Что происходит                                  |
|-------------------------------------------------------|-------------------------------------------------|
| Пара есть в routing с `active=Да`                     | Попадает в прогноз                              |
| Пара есть с `active=Нет`                              | Игнорируется                                    |
| Пара отсутствует в routing                            | Игнорируется                                    |
| SKU есть, но конкретного склада нет                   | Игнорируется                                    |
| Листа `warehouse_routing` нет в таблице               | Routing OFF, прогноз по-старому (со всеми)      |
| Запуск с `--no-routing`                               | То же — routing OFF                             |

В логах увидите:
```
Routing loaded: 47 active pairs (52 total rows) for 12 SKUs
Routing filter: kept 47 rows, dropped 134 not-in-routing
```

## Скорости по складам

Источник — лист `ym_orders_raw` (его наполняет `fetch_ym_orders.py`).
Логика отбора продаж та же, что в `aggregate_sales`:

- исключены статусы `CANCELLED`, `UNPAID`, `RESERVED`, `PLACING`;
- исключены `fake=Да`;
- учитываются по `date_created`.

Имя склада резолвится из `warehouse_id` через справочник из `stock_marketplace`.
Если ID неизвестен — fallback на `region`. Если и его нет — строка
пропускается с предупреждением в логе.

**Если `ym_orders_raw` ещё не наполнен** (например, бот только что
развёрнут и заказов в листе мало или нет), скорости по складам будут
нулевые → все позиции попадут в "нет продаж". В этом случае запускайте
с `--no-wh-speeds`, чтобы вернуться к общей скорости.

Рекомендуется: **сначала бэкфилл `fetch_ym_orders.py --from <90 дней назад>`,
потом включать routing**.

## Запуск

```bash
# Обычный запуск — фильтр + per-warehouse скорости (после развёртывания листа)
python forecast_stocks.py

# Проверить без записи
python forecast_stocks.py --dry-run -v

# Временно выключить routing (если лист сломан/в правке)
python forecast_stocks.py --no-routing

# Вернуть старое поведение скоростей
python forecast_stocks.py --no-wh-speeds

# Совсем по-старому
python forecast_stocks.py --no-routing --no-wh-speeds
```

## План разворачивания

1. Прогнать бэкфилл заказов хотя бы за 30 дней:
   ```bash
   python fetch_ym_orders.py --from 2026-04-24 --to 2026-05-24
   ```
2. Создать лист `warehouse_routing`, заполнить пары которые реально торгуются.
   Самый быстрый способ — взять текущий вывод `forecast_stocks.py --no-routing -v`,
   оставить только нужные пары, остальное пометить `active=Нет`.
3. Один раз прогнать с новой логикой в `--dry-run`:
   ```bash
   python forecast_stocks.py --dry-run -v 2>&1 | grep -E "Routing|kept"
   ```
   Проверить что число "kept" совпадает с ожиданиями.
4. Включить в cron как раньше.
