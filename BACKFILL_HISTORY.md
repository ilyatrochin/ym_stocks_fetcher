# Бэкфилл истории заказов — версия v5

## Гипотеза

Я не уверен на 100%, что лимит «30 дней» — это **жёсткое ограничение API**.
Похоже это последствие того что в коде использовалась **устаревшая структура
запроса**: `{"dates": {"fromDate": "DD-MM-YYYY"}}`, тогда как актуальная
схема — `{"dateFrom": "YYYY-MM-DD"}` (см. yandex.ru/dev/market/partner-api).

API, скорее всего, **молча игнорировал** неизвестный ему параметр `dates` и
применял дефолт — отсюда «возвращает только последние 30 дней».

В v5 я поправил запрос на актуальную схему. Эту гипотезу нужно проверить.

## Шаг 1 — Проверочный запрос с диагностикой

```bash
mkdir -p /tmp/ym_debug_history
python fetch_ym_orders.py \
    --from 2026-01-01 --to 2026-01-31 \
    --debug-json /tmp/ym_debug_history \
    --dry-run -v
```

**Смотрите в лог три строки:**

```
DEBUG: saved raw page → page_2026-01-01_2026-01-31_p001.json (... bytes)
DEBUG page 1: N orders, creationDate range 2026-01-XX..2026-01-XX (requested 2026-01-01..2026-01-31)
Pagination done after K pages
```

Возможные исходы:

### ✅ Сработало
`creationDate range` попадает в `2026-01-XX`, заказы есть.
→ Можно делать полный бэкфилл:
```bash
python fetch_ym_orders.py --from 2026-01-01 --to 2026-05-26
```

### ⚠️ Сервер вернул 0 заказов
Сработает warning:
```
WARNING: API returned 0 orders for period 2026-01-01..2026-01-31 (31 days).
```
→ Возможно: (а) у вас действительно нет заказов за январь, (б) API
требует другую структуру параметров.

Откройте файл `/tmp/ym_debug_history/page_2026-01-01_*.json` и
посмотрите, что там. Если структура странная или есть поле `error`/
`errors` — пришлите его мне.

### ⚠️ Вернулись данные, но из другого периода
`creationDate range` показывает свежие даты (`2026-04-XX..2026-05-XX`)
вместо запрошенных январских.
→ API всё ещё применяет дефолт. В этом случае действительно нужен
Reports API (см. ниже).

### ❌ HTTP-ошибка
Скрипт упадёт с `RuntimeError: HTTP 400: ...` или похожим.
→ Пришлите мне текст ошибки — там будет подсказка какой параметр
не так.

## Шаг 2 — Если шаг 1 не сработал, переходим на Reports API

Это более тяжёлый путь — асинхронная генерация XLSX-отчёта. Я подготовлю
отдельный модуль `fetch_ym_orders_history.py`, который:

1. `POST /reports/goods-realization/generate` с businessId, year, month.
2. Получает `reportId`.
3. Поллит `GET /reports/info/{reportId}` пока не `status=DONE`.
4. Скачивает XLSX по `result.file`.
5. Парсит и сливает в `ym_orders_raw` (с пометкой `source=report` чтобы не
   путать с реальными заказами — там агрегаты по месяцам).

**Минусы Reports API:**
- Данные приходят с задержкой 1–2 дня.
- Структура — агрегаты по дням, не по отдельным заказам (нет order_id).
- Минимальный шаг — месяц.
- Лимит 100 генераций отчёта/час.

**Плюс:** работает за прошлые годы.

Если шаг 1 не помог — напишите, тогда добавлю этот модуль.

## Что было исправлено в v5

| Что | Было | Стало |
|---|---|---|
| Параметр периода | `dates.fromDate` (DD-MM-YYYY) | `dateFrom` (YYYY-MM-DD) — актуальная схема API |
| `programTypes` | передавали `["FBY"]` | убрал — поле не в актуальной схеме; FBY-фильтр можно делать через `delivery.deliveryPartnerType` если потребуется |
| Защита от 0 заказов | молчала | warning в лог при пустом ответе на длинный период |
| Дебаг-режим | сохранял JSON | теперь ещё печатает `creationDate range` каждой страницы — видно, что реально вернул сервер |
