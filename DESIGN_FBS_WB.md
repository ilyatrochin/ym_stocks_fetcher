# FBS Wildberries (модуль 7.1) — проект

> Статус: **этап 1 реализован** (`fbs_wb.py`, `fbs_wb_bot.py`, только чтение); этапы 2–3 — проект. Источник по API — официальная спецификация
> `https://dev.wildberries.ru/api/swagger/yaml/ru/03-orders-fbs.yaml` (сверено 2026-10-24).
> Яндекс-часть (модуль 7: `fbs_shipment.py`, `fbs_bot_handlers.py`) **не меняется вообще**; WB — отдельный, отделимый модуль.

---

## 1. Что хотим

Из того же бота собирать FBS-отгрузку и для Яндекс.Маркета, и для Wildberries, выбирая
**где** (маркетплейс) и **как** (отдельные листы и ярлыки на каждый МП, режим поставки WB,
формат стикеров). Выбор задаётся аргументами команды, умолчания берутся из `.env`.

**У WB нет даты.** Выбирается только **склад продавца**, и в поставку собирается **всё, что
сейчас есть** в новых заданиях этого склада.

Для WB бот проходит **полный цикл**:
задания → поставка → добавление заданий → стикеры и лист сборки → параметры отгрузки →
передача в доставку → QR-код поставки.

## 2. Чем WB принципиально отличается от Яндекса

| | Яндекс (модуль 7) | Wildberries |
|---|---|---|
| Что собирать | заказы `PROCESSING/STARTED` с `shipmentDate` = дата | все задания в статусе `new` (`GET /api/v3/orders/new`), **даты отгрузки у задания нет** |
| Ярлыки | можно получить сразу, только чтение | стикеры отдаются **только** для заданий в `confirm`/`complete`, то есть **после добавления в поставку** (это запись) |
| Формат ярлыков | Маркет присылает готовый PDF | PNG/SVG/ZPL по одному на задание, по 100 за запрос → **PDF собираем сами** |
| «Собрано» | `STARTED → READY_TO_SHIP` | добавить в поставку (`new → confirm`), затем передать поставку в доставку (`confirm → complete`) |
| Группировка | по кампании | поставка привязана к **одному складу продавца**, а после первого задания ещё и к `cargoType`, `crossBorderType`, `isB2b` |
| Обязательное для отгрузки | — | с 01.10.2026 **параметры отгрузки** (`shippingType`, `shippingPointId`, `shippingDt`), без них `deliver` → 409 |
| Наименование товара | `offerName` в заказе | **нет**, есть только `article`, `nmId`, `skus` |
| Маркировка | `requiredInstanceTypes` | `requiredMeta` (sgtin/uin/imei/gtin…): без неё `deliver` не пройдёт |
| Лимиты | 420 = rate limit | 300 запросов/мин, интервал 200 мс; лимит → **429**; **любой 4XX считается за 10 запросов** |
| Авторизация | `Api-Key: …` | `Authorization: <token>` (категория токена «Маркетплейс», на запись) |

Отсюда два вывода:

1. **Кнопка «Документы» у WB не может быть только чтением.** Чтобы получить стикеры, задания
   нужно положить в поставку, а это меняет их статус на «На сборке». Поэтому для WB
   «Документы» = «взять в сборку + документы», и эта кнопка тоже доступна только
   пользователям из `TG_ALLOWED_USERS` (`_write_allowed`).
2. **У WB даты в команде нет.** У Яндекса дата — фильтр «что отгружать в этот день».
   У WB берутся **все** задания в `new` выбранного склада (плюс уже взятые в сборку, но ещё
   не переданные в доставку, из открытых поставок этого склада). Обязательный для `deliver`
   параметр `shippingDt` бот ставит сам: **сегодня** по `FBS_TZ`. Пользователь его не вводит.
   Логику просрочек Яндекса (`OVERDUE_LOOKBACK_DAYS`) для WB **не переносим**.

## 3. API WB, которое используем (только из официального yaml)

Хост: `https://marketplace-api.wildberries.ru` (песочница: `marketplace-api-sandbox.wildberries.ru`, 1 запрос/сек).

| Шаг | Метод | Путь | Заметки |
|---|---|---|---|
| Склады продавца | GET | `/api/v3/warehouses` | для выбора склада (ID + название) |
| Новые задания | GET | `/api/v3/orders/new` | без пагинации, все «на момент запроса» |
| Задания по периоду | GET | `/api/v3/orders` | `limit`/`next`/`dateFrom`/`dateTo`, только 3 мес. (старше — `/api/marketplace/v3/fbs/orders/archive`) |
| Статусы | POST | `/api/v3/orders/status` | `supplierStatus` (`new/confirm/complete/cancel`) + `wbStatus`; перепроверка отмен |
| Поставки (список) | GET | `/api/v3/supplies` | `limit` (≤1000) + `next` (с 0), **фильтра по `done` нет**, фильтруем сами |
| Создать поставку | POST | `/api/v3/supplies` | `{"name": "..."}` (≤128 симв.) → `{"id": "WB-GI-…"}` |
| Добавить задания | PATCH | `/api/marketplace/v3/supplies/{supplyId}/orders` | `{"orders": [...]}` **до 100**, 204; переводит в `confirm`. Старый `PATCH /api/v3/supplies/{id}/orders/{orderId}` отключён |
| Задания поставки | GET | `/api/marketplace/v3/supplies/{supplyId}/order-ids` | для сверки и повторного запуска |
| Стикеры | POST | `/api/v3/orders/stickers?type=png&width=58&height=40` | `{"orders": [...]}` до 100; размеры 58×40 или 40×30 |
| Маркировка (чтение) | POST | `/api/marketplace/v3/orders/meta` | какие задания ещё без КИЗ |
| Пункты отгрузки | GET | `/api/marketplace/v3/fbs/supplies/{supplyId}/shipping-points` | общий `/api/marketplace/v3/fbs/shipping-points` — **deprecated** |
| Параметры отгрузки | PATCH | `/api/marketplace/v3/fbs/supplies/shipping-method` | `data: [{supplyId, shippingDt, shippingPointId, shippingType}]`, до 100 поставок |
| ЭТрН | PATCH | `/api/marketplace/v3/fbs/supplies/waybill` | только для `transportCompany`; **на этапе 3 не делаем**, см. §9 |
| Грузоместа (ПВЗ) | POST | `/api/v3/supplies/{supplyId}/trbx` | `{"amount": N}` → `trbxIds`; только для поставок в ПВЗ, обязательно |
| Стикеры грузомест | POST | `/api/v3/supplies/{supplyId}/trbx/stickers?type=png` | 580×400 (= 58×40) |
| В доставку | PATCH | `/api/v3/supplies/{supplyId}/deliver` | закрывает поставку, задания → `complete`; 409 без параметров отгрузки |
| QR поставки | GET | `/api/v3/supplies/{supplyId}/barcode?type=png` | печатается после передачи в доставку |

## 4. Модель «где и как собирать»: склад и режим поставки

**Склад — главный выбор.** Сбор всегда идёт по одному складу продавца (`warehouseId`),
список складов берётся из `GET /api/v3/warehouses`:

- `/fbs_wb <склад>` — по ID или части названия («офис», «москва»);
- `/fbs_wb` без склада: если новые задания есть только на одном складе (или задан
  `FBS_WB_WAREHOUSE`), берём его; иначе бот показывает кнопки складов с числом заданий
  («🏬 Офис — 14», «🏬 Склад 2 — 3»);
- в поставку уходят **все** новые задания склада, без фильтров по дате.

Внутри склада задания группируются по ключу **`(warehouseId, cargoType, crossBorderType, isB2b)`**. Это
ограничение самого WB, а не наш выбор. К ключу добавлен **`isPickupPointShipmentAllowed`**: отгрузка
по умолчанию идёт в ПВЗ (§4.1), а задания «не для ПВЗ» везутся отдельной поставкой на СЦ/склад WB
(бот показывает их отдельной группой с предупреждением).
Режимы определяют, как группы превращаются в поставки:

| Режим (`FBS_WB_SUPPLY_MODE` / аргумент) | Поведение |
|---|---|
| `auto` (по умолчанию) | Для каждой группы ищем **открытую** поставку (`done=false`, тот же склад и признаки, ещё не отсканирована). Есть — дополняем, нет — создаём `FBS {склад} {ДД.ММ ЧЧ:ММ}`. Обычно на складе одна группа, а значит одна поставка. Повторное нажатие не плодит дубли. Поставки, созданные руками в кабинете, тоже переиспользуются. |
| `new` | Всегда новая поставка на группу (например, вторая машина за день). |
| `supply=WB-GI-…` | Всё в указанную поставку; задания, не подходящие по ключу, уходят в «Не в листе» с причиной. |

Задания других складов в сводку не попадают. Внизу показывается только строка «На других
складах: Склад 2 — 3 задания → /fbs_wb склад2».

### 4.1. Отгрузка по умолчанию: сами, в ПВЗ (решение от 2026-10-24)

- `shippingType = selfShipping`, пункт отгрузки — **ПВЗ** (`officeType = pp`), `shippingDt` = сегодня.
- Пункт берётся из `FBS_WB_SHIPPING_POINT_ID`. Если не задан, бот показывает кнопками
  ПВЗ из `GET /api/marketplace/v3/fbs/supplies/{supplyId}/shipping-points` (только `officeType=pp`
  и `available=true`). `available=false` означает, что ПВЗ перегружен на эту дату: бот предлагает другой.
- **Грузоместа обязательны для ПВЗ.** Без них `deliver` → `FulfillmentSupplyBoxesRequired`.
  Число мест **спрашивается у человека после сборки поставки**, когда видно, сколько единиц в
  ней сейчас (решение от 2026-10-24, см. §4.2). WB ограничивает число: не больше
  половины заданий (10 заданий → ≤ 5 мест). Что WB разрешает для 1 задания, в спецификации не
  сказано: проверить в песочнице. Распределять задания по коробам API не требует.

### 4.2. Порядок шагов (решение от 2026-10-24)

```
1. 📦 Собрать поставку     → поставка (auto: открытая или новая) + все новые задания склада
                             → стикеры заданий 58×40 + лист сборки → чат и Drive
                             → «Поставка WB-GI-… : сейчас N шт (N заданий). Сколько грузомест?»
2. Сколько мест? [1][2][3][4][5][6] (не больше max(1, N // 2); другое — /fbs_wb_boxes WB-GI-… 8)
                           → POST …/trbx {"amount": K} → стикеры грузомест 58×40 → чат и Drive
3. 🚛 Сдать в ПВЗ           → подтверждение → shipping-method (сами, ПВЗ, сегодня) → deliver → QR
```

- Шаг 2 повторяем, если после шага 1 пришли новые задания: «Собрать поставку» ещё раз
  добавит их в ту же открытую поставку и снова покажет «сейчас N шт».
- Если у поставки **уже есть** грузоместа (`GET …/trbx`), на шаге 2 бот показывает
  «уже K мест» и предлагает: **[🖨 Перепечатать K]**, **[➕ Добавить]** или
  **[♻️ Пересоздать]** (`DELETE …/trbx`, потом новые). Так повторное нажатие не плодит лишние места.
- «Сдать в ПВЗ» недоступна, пока у поставки нет ни одного грузоместа (кнопка не показывается).
- Задания с `isPickupPointShipmentAllowed=false` в ПВЗ-поставку не кладутся. Они идут в
  отдельную группу «не для ПВЗ», и пункт для неё (СЦ/склад) бот спросит отдельно.

## 5. Команды бота

`/fbs` и `/fbs_check` остаются **Яндексом без изменений**: `fbs_bot_handlers.py` не трогаем.
Выбор МП — это выбор команды. У WB свои команды, которые живут в своём файле:

```
/fbs [дата]                      — Яндекс, как сейчас (не меняется)
/fbs_wb [склад] [режим] [стикер=58x40|40x30|zpl]   — WB, без даты: всё новое на складе
/fbs_wb_check <id> [id…]         — разбор заданий WB: supplierStatus/wbStatus, склад, поставка, почему не в листе
/fbs_wb_boxes <WB-GI-…> <K>      — задать число грузомест вручную (если больше, чем есть кнопок)
```

Общей команды «YM + WB» нет: она связала бы модули. Разбор аргументов `/fbs_wb`:
`key=value`, затем режим (`auto|new`), остаток считается складом. Если аргумент похож на дату,
отвечаем «у WB даты нет, собирается всё новое».

### Кнопки WB (префикс callback `fbswb:`)

Префикс `fbswb:` не пересекается с `^fbs:` Яндекса, поэтому обработчики не мешают друг другу.
Порядок шагов зашит в кнопки, переход вперёд только после успеха предыдущего шага:

```
🚚 FBS WB · склад «Офис» · 14 заданий
   [📦 Собрать поставку (14)]        ← поставка + задания + стикеры заданий + лист → чат и Drive

✅ Поставка WB-GI-123 «FBS Офис 24.10 15:10»: сейчас 14 шт (14 заданий)
   Сколько грузомест?  [1] [2] [3] [4] [5] [6]
                                     ← trbx → стикеры грузомест → чат и Drive

📦 WB-GI-123: 14 шт, 2 грузоместа
   [🚛 Сдать в ПВЗ]  [🖨 Перепечатать места]  [♻️ Пересоздать места]
```

- `callback_data` ≤ 64 байт. Сводка и выбор склада: `fbswb:<action>:<warehouseId>`. Шаги по
  поставке несут её ID: `fbswb:box:<supplyId>:<K>`, `fbswb:deliver:<supplyId>` (≤ 40 байт).
  Перед любым действием поставка перечитывается из API: если она уже закрыта, бот так и скажет.
- Все кнопки записи проверяют свой `_write_allowed` (та же логика fail-closed по
  `TG_ALLOWED_USERS`, но в коде WB, а не импорт из YM). «Передать в доставку» всегда спрашивает
  подтверждение и передаёт только поставки, показанные в подтверждении (как «Собрано» у YM).
- Задания с незаполненным `requiredMeta` блокируют `deliver` для всей поставки. Бот
  показывает их списком и не пытается передать такую поставку (КИЗ вводится в кабинете, как у YM).

## 6. Документы WB

- **Лист сборки** рисует свой `build_wb_picking_pdf` в `fbs_wb.py` (reportlab, DejaVu). Вёрстка
  та же, что у YM (подбор по SKU + упаковка по заданиям), но код свой, без импорта из
  `fbs_shipment.py`. Заголовок: «Лист сборки FBS WB — склад X — поставка WB-GI-…».
- **Стикеры**: **58×40** (решение от 2026-10-24, как у Яндекса). PNG по 100 за запрос → один PDF,
  страница 58×40 мм, **в порядке листа сборки**. 40×30 и ZPL остаются опцией `стикер=…`, но по
  умолчанию не используются.
- **Стикеры грузомест** (только для ПВЗ): PNG 580×400 → PDF 58×40, после создания мест.
- **QR поставки** (после `deliver`): PNG → PDF 58×40, отправляется в чат и на Drive.
- **Google Drive — своя папка WB**: `GDRIVE_FBS_WB_FOLDER_ID` (тоже на общем диске, SA —
  «Менеджер контента»). Папка Яндекса `GDRIVE_FBS_FOLDER_ID` не трогается. Внутри — подпапка
  дня сборки `YYYY-MM-DD/` (дата формирования, а не фильтр), файлы:
  `picking_<supplyId>.pdf`, `stickers_<supplyId>.pdf`, `qr_<supplyId>.pdf`. Ключ имени — поставка,
  поэтому повторный запуск по той же поставке перезаписывает файлы, а новая поставка в тот же
  день добавляет свои. Загрузчик Drive у WB свой (копия `DriveUploader`), YM-шный не импортируется.
- **Наименование товара**: в заданиях WB его нет. Берём из листа `products` в Google Sheets
  (по `article`, только чтение), если не нашли — показываем `article` + `nmId`.
  Content API не подключаем: ему нужен токен другой категории.

## 7. Отделение от Яндекса (структура кода)

```
fbs_shipment.py      ← YM — НЕ МЕНЯЕТСЯ
fbs_bot_handlers.py  ← YM — НЕ МЕНЯЕТСЯ
fbs_wb.py            ← НОВЫЙ: модели WbOrder/WbPlan, WBFbsClient, план по складу, поставки,
                       стикеры, лист сборки PDF, Drive, deliver; CLI (--dry-run/--fixture/--explain)
fbs_wb_bot.py        ← НОВЫЙ: /fbs_wb, /fbs_wb_check, кнопки fbswb:*; register_fbs_wb_handlers(app, …)
tg_supplies_bot.py   ← +1 строка регистрации WB (как у YM), под флагом
```

Принцип — **модули полностью независимы в обе стороны**:

- **Ни одного импорта между YM и WB.** `fbs_wb*.py` не импортирует `fbs_shipment` /
  `fbs_bot_handlers`, и наоборот. Общие куски (шрифты, вёрстка листа, `DriveUploader`,
  `parse_ship_date`-подобные утилиты, `_write_allowed`) **копируются** в WB-модуль. Дублирование
  ~200 строк — осознанная цена за то, что любой модуль можно удалить или переписать, не трогая другой.
- **Удаление WB** = удалить `fbs_wb.py`, `fbs_wb_bot.py` и строку регистрации. Яндекс не замечает.
- **Подключение в боте** — одна строка, и падение WB не роняет бота:
  ```python
  if os.environ.get("WB_API_TOKEN"):
      try:
          from fbs_wb_bot import register_fbs_wb_handlers
          register_fbs_wb_handlers(app, is_allowed=_is_allowed)
      except Exception:
          logging.exception("WB FBS handlers not loaded")
  ```
  Без `WB_API_TOKEN` модуль WB не грузится вовсе.
- **Свои структуры данных**: `WbOrder` (`order_id`, `warehouse_id`, `article`, `nm_id`,
  `cargo_type`, `cross_border`, `is_b2b`, `required_meta`, `supply_id`, `sticker` partA/partB),
  `WbPlan`. Модели YM (`FbsOrder` с `campaign_id`/`substatus`) не переиспользуем: у них другая семантика.
- **Свои env и папки**: только `WB_*` / `FBS_WB_*` / `GDRIVE_FBS_WB_FOLDER_ID`. Общие с ботом
  только `TG_ALLOWED_USERS`, `GOOGLE_CREDS`, `FBS_TZ`, `FBS_FONT_PATH` (их только читаем).
- **Отдельный HTTP-клиент** `WBFbsClient` (копировать `YMFbsClient._request` нельзя: другие
  коды лимитов). Ретраи 429/5xx, пауза ≥ 200 мс между запросами, на 4XX не ретраим
  (каждый 4XX съедает 10 из 300 запросов лимита). `WBApiError(status_code, text)`.
- **Ключи**: `WB_API_TOKEN` (категория «Маркетплейс», запись). Ошибка 401/403 → подсказка о
  категории и правах токена (свой текст ошибки, по образцу YM).

## 8. Безопасность и идемпотентность

- CLI `fbs_wb.py` по умолчанию **только читает**: показывает сводку и задания и строит лист
  сборки без стикеров. Запись — только с явным `--take` (поставка + стикеры) и `--deliver`.
  Для отладки записи `--sandbox` переключает хост на песочницу.
- Повторный «Собрать поставку» берёт уже `confirm`-задания из открытых поставок и добавляет
  только новые `new`, поэтому дублей не будет.
- Перед стикерами и перед `deliver` перечитываются статусы (`/api/v3/orders/status`):
  отменённые (`cancel`, `canceled*`) исключаются из стикеров и показываются отдельно.
- Каждое действие записи логируется так же, как у YM: `FBS WB <action> by <user> (<id>): supply=… ok=… failed=…`.
